An app supplies UI for the [slots](/concepts/slots) in its contract. A view defines what to show in a slot for a particular [context](/concepts/views).

These examples assume your app is configured to use that contract. Generate its bindings after adding or changing capabilities:

```sh
npx patchsmith generate
```

## Write a view

Put view files in `slots/<slot>/` with a `.view.tsx` suffix. This view supplies default UI for the `panel` slot:

```tsx title="slots/panel/index.view.tsx"
import "../../patchsmith.gen";
import { defineView } from "patchsmith/client";

const view = defineView({
  slot: "panel",
  view: "/",
  component: Overview,
});

function Overview() {
  return "Member overview";
}

export default view;
```

The folder identifies the slot. The filename identifies the context: `index.view.tsx` maps to `/`, and `members/detail.view.tsx` or `members.detail.view.tsx` maps to `/members/detail`. An explicit `view` gives `useContext()` its inferred type and must match that path. The build rejects mismatched `view` or `slot` declarations.

## Shared shell and layouts

Put providers and UI shared by all slots in `slots/root.tsx`. The shell renders `Route` to show the selected view:

```tsx title="slots/root.tsx"
import { ClientProvider, defineRoute, Route } from "patchsmith/client";

const Shell = () => (
  <ClientProvider>
    <Route />
  </ClientProvider>
);

export default defineRoute({ shellComponent: Shell });
```

Use `slots/<slot>/root.tsx` for a shell specific to one slot and `slots/<slot>/layout.tsx` for its layout. Apps using the optional `src/` directory keep this same hierarchy under `src/slots/`.

## Use components and tools

Add another view for `/members/detail`. With `Button` and `showToast` exposed in the contract, generated imports let you use them together:

```tsx title="slots/panel/members.detail.view.tsx"
import { defineView } from "patchsmith/client";
import { Button, tools } from "../../patchsmith.gen";

const view = defineView({
  slot: "panel",
  view: "/members/detail",
  component: MemberDetails,
});

function MemberDetails() {
  const { member } = view.useContext();

  return (
    <Button
      variant="secondary"
      onClick={() => tools.showToast({ message: "Selected " + member.name })}
    >
      {member.name}
    </Button>
  );
}

export default view;
```

On a member's page, Patchsmith selects this view and supplies the member context. Elsewhere, the panel can fall back to the overview. The button's click callback calls a client tool that shows a toast.

## Supply several instances

For a `tile` slot declared with `multiple: true`, return an entry for each dashboard tile:

```tsx title="slots/tile/index.view.tsx"
import "../../patchsmith.gen";
import { defineView } from "patchsmith/client";
import { z } from "zod";

const view = defineView({
  slot: "tile",
  view: "/",
  component: Tile,
  instances: {
    cache: "static",
    dataSchema: z.object({ title: z.string(), value: z.number() }),
    resolve: () => [
      {
        key: "members",
        metadata: { position: { column: 1, row: 1 } },
        data: { title: "Members", value: 12 },
      },
      {
        key: "tasks",
        metadata: { position: { column: 2, row: 1 } },
        data: { title: "Open tasks", value: 8 },
      },
    ],
  },
});

function Tile() {
  const { data } = view.useInstance();
  return data.title + ": " + data.value;
}

export default view;
```

`useInstance()` reads the selected entry in the UI. The surrounding dashboard decides how to use `position` metadata.

### Choose when instances resolve

Use `cache: "static"` for fixed entries like the example above. The build calls the resolver once, validates each entry with `dataSchema`, and stores the parsed results in the deployment manifest. The platform returns those entries during discovery without issuing an app session or calling the Cloudflare app runtime. A new deployment replaces the snapshot.

Static resolvers can be async and can import build-time helpers. They take no arguments: request context, identity, registered queries, and cancellation signals are unavailable. Keep their parsed data and metadata JSON-compatible. Dates, big integers, functions, cycles, and `undefined` values fail the build. Each resolver can return up to 1,000 entries with unique, nonempty keys; an empty array is a valid static snapshot. Resolver errors and invalid output fail the build without falling back to runtime execution.

Static output is deployment metadata shared by installations of that deployment. Keep private values out of the returned entries. Host authentication, scope filtering, view selection, and context readiness checks still apply. Queries made by the rendered UI still use the app runtime.

For entries that depend on a request or app data, omit `cache` or set `cache: "none"`. The resolver then runs on the app server and can use the current context, identity, and registered queries. `"none"` controls server-side resolver execution; the host client's existing response cache still applies independently. Runtime cache lifetime objects are not supported yet.

For a repeatable page slot, use the same pattern with keys such as `reports` and `activity`, and metadata such as `{ label: "Reports", icon: "chart" }` for sidebar links.

## SDK reference

Import `defineView` from `patchsmith/client`. The build discovers `.view.tsx` files and extracts instance resolvers into the server bundle.

| Option | Meaning |
| --- | --- |
| `slot` | Must match `slots/<slot>/` if supplied. Otherwise the build uses the folder name. |
| `view` | A supported context path matching the filename. Optional; when supplied, gives precise context typing. Dots and subdirectories separate path segments; a final `index` is omitted. |
| `component` | Required. The UI component; use `view.useContext()` to read its context. |
| `instances` | Required for `multiple: true` slots; omitted for single-instance slots. |
| `instances.dataSchema` | Validates each entry's data. |
| `instances.cache` | `"none"` (default) resolves on the app server; `"static"` resolves during the build. |
| `instances.resolve` | Returns entries or a promise of entries. Static resolvers take no arguments. |

The resolver receives `{ context, identity, signal, queries }`. It can call registered queries; actions and mutations are unavailable there.

Each entry needs a stable, non-empty key unique within its view, a metadata object, and data matching `dataSchema`. Use metadata for labels or placement hints and data for values the view renders:

```ts
export interface ViewInstance<TData = unknown> {
  key: string;
  metadata: Record<string, unknown>;
  data: TData;
}
```

`view.useInstance()` reads the selected entry, with its data type inferred from `dataSchema`.

## Frequently asked questions

View filenames determine context paths. Instance metadata describes labels and placement; instance data supplies rendered values.

<AccordionGroup>
  <Accordion title="Does naming a file index.view.tsx make it the default view?">
    Yes. `index.view.tsx` produces `/`; `members/index.view.tsx` produces
    `/members`. Explicit `view` values must agree with the file path. Only
    `.view.tsx` files register views.
  </Accordion>
  <Accordion title="Where do instance labels and layout rules belong?">
    Return labels, icons, or placement hints in `metadata`. The surrounding UI
    uses them to build links or arrange tiles. Put values your view needs to
    render in `data`.
  </Accordion>
</AccordionGroup>
